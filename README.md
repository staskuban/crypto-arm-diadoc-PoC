# КриптоАРМ + Контур.Диадок: подписание и отправка УПД

Proof of concept конвейера для УПД (универсальный передаточный документ, формат ФНС 5.03):

1. Ключи и сертификаты хранятся централизованно в **КриптоАРМ Server** (Docker, КриптоПро CSP 5.0).
2. Документ подписывается через `POST /cms/sign` КриптоАРМ Server — открепленная подпись CAdES-BES.
3. Подписанный документ вместе с подписью отправляется контрагенту через публичный API **Контур.Диадок**.

Используются только публичные API обеих систем. Базы данных нет: ключи живут в КриптоАРМ Server, состояние
документооборота — в Диадоке.

```
<ИдФайл>.xml ──► parse ──► КриптоАРМ Server /cms/sign ──► /cms/verify + политика подписи
                                                                  │
   JSON-результат ◄── опрос DocflowStatus ◄── PostMessage ◄── CanPostMessage (+ полка для файлов ≥ 500 000 B)
```

## Что нужно

| Что                                     | Зачем / где взять                                                                                                                 |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Node.js 22 LTS, npm                     | CLI на хосте (`.nvmrc`)                                                                                                           |
| Docker + Compose ≥ 2.24                 | стенд КриптоАРМ Server и CLI в контейнере; образ только `linux/amd64` (на Apple Silicon — эмуляция)                               |
| КриптоПро CSP 5.0 `linux-amd64_deb.tgz` | скачать вручную с cryptopro.ru (нужен логин) в `docker/cryptoarm-server/cryptopro/`                                               |
| Лицензия КриптоАРМ Server               | **обязательна**: без нее сервер не стартует (`Trusted Crypto license is invalid`)                                                 |
| Лицензия КриптоПро CSP                  | необязательна: без нее CSP работает в демо-режиме 90 дней                                                                         |
| Доступ к API Диадока                    | «Кабинет интегратора»: `client_id`, API-ключ (= `client_secret`), `refresh_token`; сервисная учетка с правом отправлять документы |
| Ящики Диадока                           | ID ящика отправителя и получателя; получатель должен быть контрагентом отправителя                                                |

## Быстрый старт

### Короткий путь: первый документ в Диадоке без стенда

Проверяет доступ к Диадоку, ящики и формат УПД. Подписывает Диадок своим тестовым сертификатом, поэтому КриптоАРМ
Server и КриптоПро на этом шаге не нужны. Нужны два тестовых ящика и доступ к API (см. [Конфигурация](#3-конфигурация-конвейера)).

```sh
npm ci && npm run build
(umask 077; cp .env.example .env)                                     # заполнить DIADOC_* (см. ниже)
(umask 077; printf '%s' '<refresh_token>' > .diadoc-refresh-token)    # и DIADOC_REFRESH_TOKEN_FILE=./.diadoc-refresh-token в .env

npm run cli -- make-test-utd                                          # → utd/<ИдФайл>.xml
SIGNER_KIND=diadoc-test npm run cli -- send utd/<ИдФайл>.xml          # → код 0, «Ожидается подпись контрагента»
```

Документ появится во входящих ящика получателя в веб-интерфейсе Диадока. Дальше — полный путь с подписью
КриптоАРМ Server (шаги 1–5).

### 1. Установка и сборка

```sh
npm ci
npm run build
npm test          # юнит-тесты
npm run lint
```

### 2. Стенд КриптоАРМ Server

Все команды — из корня репозитория.

```sh
# КриптоПро CSP, скачанный вручную
cp ~/Downloads/linux-amd64_deb.tgz docker/cryptoarm-server/cryptopro/

# тестовые сертификаты (сертификат + ключ CN=cryptoarm.server.test и корень тестового УЦ КриптоПро)
scripts/fetch-test-certs.sh

# настройки стенда и секреты (все файлы git-ignored)
(umask 077; cp docker/cryptoarm-server/.env.example docker/cryptoarm-server/.env)
(umask 077; printf '%s' '<лицензия КриптоАРМ Server>' > docker/cryptoarm-server/secrets/trusted_license)
(umask 077; openssl rand -hex 24 > docker/cryptoarm-server/secrets/api_keys)

# сборка образа и запуск
docker compose build cryptoarm-server-image
docker compose up -d --wait cryptoarm-server
docker compose ps cryptoarm-server             # должен быть healthy

# проверка: подписать и проверить случайные данные
CRYPTOARM_SERVER_API_KEY="$(head -1 docker/cryptoarm-server/secrets/api_keys)" SMOKE_STRICT=1 \
  scripts/smoke-server.sh
```

Swagger сервера: http://localhost:3037/docs.

Необязательно: выпустить в тестовом УЦ КриптоПро сертификат организации (ИНН/ОГРН в сертификате, ключ создается
внутри контейнера и не экспортируется):

```sh
scripts/issue-test-cert.sh    # → docker/cryptoarm-server/certs/o2-platforma.test.cer
```

Подробности (секреты, свои ключи `.pfx`, обновление и откат стенда, hardening):
[docker/cryptoarm-server/README.md](docker/cryptoarm-server/README.md).

### 3. Конфигурация конвейера

```sh
(umask 077; cp .env.example .env)
(umask 077; printf '%s' '<refresh_token>' > .diadoc-refresh-token)
```

Минимальный `.env` для отправки с подписью КриптоАРМ Server:

```dotenv
# --- КриптоАРМ Server ---
CRYPTOARM_SERVER_URL=http://localhost:3037
CRYPTOARM_SERVER_API_KEY=<первая строка docker/cryptoarm-server/secrets/api_keys>
SIGNER_CERT_PATH=./docker/cryptoarm-server/certs/cryptoarm.server.test.cer
SIGNER_KIND=server

# --- Контур.Диадок ---
DIADOC_API_URL=https://diadoc-api.kontur.ru
DIADOC_CLIENT_ID=<client_id из кабинета интегратора>
DIADOC_CLIENT_SECRET=<API-ключ из кабинета интегратора>
DIADOC_REFRESH_TOKEN_FILE=./.diadoc-refresh-token
DIADOC_FROM_BOX_ID=<GUID ящика отправителя>
DIADOC_TO_BOX_ID=<GUID ящика получателя>
```

#### Переменные

**КриптоАРМ Server (подпись)**

| Переменная                           | Обяз. | Что это                                                                                                                                                                           |
| ------------------------------------ | :---: | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CRYPTOARM_SERVER_URL`               |  да   | Адрес КриптоАРМ Server. `https`; `http` разрешен только для `localhost`, `127.0.0.1`, `[::1]` и имени сервиса `cryptoarm-server` в compose.                                       |
| `CRYPTOARM_SERVER_API_KEY`           |  да   | Ключ из `docker/cryptoarm-server/secrets/api_keys`. Заглушки `changeme` / `change-me-api-key` отклоняются. Пусто — только для сервера с `AUTH_MODE=none`.                         |
| `SIGNER_CERT_PATH`                   |  да   | **Публичный** сертификат подписанта (`.cer`, DER или PEM). Закрытый ключ остается в хранилище сервера и находится по отпечатку. `.pfx`/`.p12` отклоняются.                        |
| `SIGNER_KIND`                        |  нет  | `server` (по умолчанию) — подпись КриптоАРМ Server. `diadoc-test` — без нашей подписи, Диадок подписывает своим тестовым сертификатом; только если оба ящика тестовые (`IsTest`). |
| `CRYPTOARM_SERVER_TIMEOUT_MS`        |  нет  | Таймаут запроса к серверу, мс (по умолчанию 120000).                                                                                                                              |
| `CRYPTOARM_SERVER_MAX_REQUEST_BYTES` |  нет  | Максимальное тело запроса, байт (по умолчанию 52428800). Держать равным `JSON_LIMIT` сервера. Практический предел файла ≈ 39,3 МБ.                                                |

**Контур.Диадок (отправка)**

| Переменная                  | Обяз. | Что это                                                                                                                                                                           |
| --------------------------- | :---: | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DIADOC_API_URL`            |  да   | Хост API. Боевой: `https://diadoc-api.kontur.ru`. Тестовые ящики (форма `diadoc.kontur.ru/easyregistration`) — это `IsTest`-организации **на боевом хосте**; staging их не знает. |
| `DIADOC_CLIENT_ID`          |  да   | `client_id` из кабинета интегратора.                                                                                                                                              |
| `DIADOC_CLIENT_SECRET`      |  да   | API-ключ из кабинета интегратора.                                                                                                                                                 |
| `DIADOC_REFRESH_TOKEN_FILE` | да\*  | Файл с `refresh_token` (рекомендуется): новый токен после ротации записывается обратно. Обычный файл, не symlink; на время запуска берется `<файл>.lock`.                         |
| `DIADOC_REFRESH_TOKEN`      | да\*  | Сам токен, если файла нет (\* нужно одно из двух). Ротированный токен при этом не сохраняется.                                                                                    |
| `DIADOC_FROM_BOX_ID`        |  да   | GUID ящика отправителя.                                                                                                                                                           |
| `DIADOC_TO_BOX_ID`          |  да   | GUID ящика получателя (должен отличаться от отправителя).                                                                                                                         |
| `DIADOC_TOKEN_URL`          |  нет  | OIDC token endpoint, по умолчанию `https://identity.kontur.ru/connect/token`.                                                                                                     |
| `DIADOC_TIMEOUT_MS`         |  нет  | Таймаут одного запроса к API Диадока, мс (по умолчанию 60000).                                                                                                                    |

**Конвейер**

| Переменная                         | По умолчанию | Что это                                                                                                  |
| ---------------------------------- | :----------: | -------------------------------------------------------------------------------------------------------- |
| `PIPELINE_PRECHECK`                |    `true`    | Проверять отправку через `CanPostMessage` после подписи, перед отправкой.                                |
| `PIPELINE_STATUS_TIMEOUT_MS`       |    60000     | Сколько ждать итогового статуса документооборота (0 — прочитать один раз).                               |
| `PIPELINE_STATUS_INITIAL_DELAY_MS` |     2000     | Первая пауза опроса статуса; дальше экспоненциально.                                                     |
| `PIPELINE_STATUS_MAX_DELAY_MS`     |    30000     | Максимальная пауза опроса.                                                                               |
| `UTD_DIR`                          |   `./utd`    | Каталог с УПД на хосте: сюда пишет `make-test-utd`, в Docker он монтируется read-only рабочим каталогом. |

Значения без кавычек обрезаются на `#` (`node --env-file`): такие значения берите в кавычки или используйте `*_FILE`.
Полный список с комментариями — [.env.example](.env.example).

### 4. Где взять XML УПД

Конвейер **не формирует УПД**: он подписывает и отправляет уже готовый XML-файл. Файл должен быть титулом продавца
УПД в формате ФНС 5.03 (приказ ЕД-7-26/970@, XSD `ON_NSCHFDOPPR_1_997_01_05_03_05`, копия лежит в
`src/utd/fixtures/`), в кодировке `windows-1251`.

Откуда он берется:

| Источник                              | Когда использовать                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Выгрузка из учетной системы (1С, ERP) | Основной сценарий: учетная система выгружает УПД в формате ФНС в каталог, конвейер отправляет его.                                                                                                                                                                                                                                                                                                                                                   |
| Метод Диадока `GenerateTitleXml`      | Нет учетной системы: Диадок сам собирает корректный XML по упрощенному описанию документа. `POST /GenerateTitleXml?boxId=<ящик отправителя>&documentTypeNamedId=UniversalTransferDocument&documentFunction=СЧФДОП&documentVersion=utd970_05_03_01&titleIndex=0`, тело — пример `spikes/diadoc/fixtures/user-data-s1.xml`; имя файла приходит в `Content-Disposition`. У организаций обязательно должен быть адрес (хотя бы `RussianAddress Region`). |
| `npm run cli -- make-test-utd`        | Тестовые ящики: CLI берет реквизиты продавца (`DIADOC_FROM_BOX_ID`) и покупателя (`DIADOC_TO_BOX_ID`) из `GetOrganization` и собирает минимальный СЧФДОП, валидный по XSD. См. ниже.                                                                                                                                                                                                                                                                 |
| Пример в репозитории                  | `src/utd/fixtures/ON_NSCHFDOPPR_….xml` — для юнит-тестов разбора. Реквизиты в нем выдуманные (ИНН 7700000016/7700000023), к вашим ящикам они не относятся — для отправки не годится.                                                                                                                                                                                                                                                                 |

#### Тестовый УПД для ваших ящиков

```sh
npm run cli -- make-test-utd                      # → utd/<ИдФайл>.xml
npm run cli -- make-test-utd --out=/path/to/dir   # другой каталог
npm run cli -- make-test-utd --min-bytes=600000   # добить строками товаров до размера (проверка полки Диадока)
```

Нужны переменные `DIADOC_*` из `.env` (заданные `PIPELINE_*` тоже проверяются); стенд КриптоАРМ Server не требуется.
Файл пишется в `--out`, а без него — в `UTD_DIR` (по умолчанию `./utd`). Оба ящика должны быть тестовыми
(`IsTest`), иначе команда отказывается с `error [TEST_UTD_REFUSED]`, чтобы выдуманный документ не ушел реальному
контрагенту. В stdout печатается JSON с путем к файлу, в stderr — готовая команда `send` для него:

```json
{
  "path": "utd/ON_NSCHFDOPPR_2BM-…_2BM-…_20260927_457815f4-…_0_0_0_0_0_00.xml",
  "fileName": "ON_NSCHFDOPPR_2BM-…_2BM-…_20260927_457815f4-…_0_0_0_0_0_00.xml",
  "bytes": 1756,
  "seller": { "name": "Тестовая организация №…", "inn": "…", "kpp": "…" },
  "buyer": { "name": "Тестовая организация №…", "inn": "…", "kpp": "…" }
}
```

Каждый запуск создает новый файл (новый GUID в `ИдФайл`) — значит, и новый документ при отправке. Существующий
файл никогда не перезаписывается. Коды выхода: 0 — записан, 1 — ошибка (`TEST_UTD_REFUSED`, `TEST_UTD_FAILED`,
`DIADOC_AUTH`, `WRITE_FAILED`, `PIPELINE_CONFIG`, `DIADOC_CONFIG`, `INTERRUPTED`), 2 — неверные аргументы.
`--min-bytes` — не больше 40 000 000 (предел подписи КриптоАРМ Server ≈ 39,3 МБ). Каталог `utd/` в `.gitignore`.
`Подписант` в тестовом УПД — заглушка «Тестов Тест, Директор».

#### Требования к файлу

CLI проверяет перед подписанием:

- имя файла = атрибут `Файл/@ИдФайл` + `.xml` (например,
  `ON_NSCHFDOPPR_<FnsParticipantId покупателя>_<FnsParticipantId продавца>_<ГГГГММДД>_<GUID>_0_0_0_0_0_00.xml`);
- это титул продавца (КНД 1115131), версия формата 5.03, `Документ/@Функция` — `СЧФ`, `ДОП`, `СЧФДОП`, `СвРК`
  или `СвЗК`;
- есть блок `Подписант`: он заполняется до подписания, после подписи файл менять нельзя.

CLI **не** сверяет стороны документа с ящиками. Продавцом в УПД должна быть организация ящика `DIADOC_FROM_BOX_ID`,
а покупателем — `DIADOC_TO_BOX_ID`. Реквизиты ящика (ИНН, КПП, `FnsParticipantId`) отдаёт метод Диадока
`GetOrganization?boxId=`. Полной проверки по XSD CLI тоже не делает: она на стороне учетной системы или `GenerateTitleXml`.

Файл подписывается и отправляется байт в байт: не открывайте и не пересохраняйте его в редакторе, который меняет
кодировку или переводы строк.

### 5. Подписать и отправить УПД

```sh
npm run cli -- send utd/ON_NSCHFDOPPR_<...>.xml
```

Что происходит: разбор УПД → проверка срока действия сертификата → `/cms/sign` → `/cms/verify` и политика
подписи (DER, открепленная, один подписант = `SIGNER_CERT_PATH`) → `CanPostMessage` → `PostMessage` (файлы от
500 000 B — через полку Диадока, больше 3 000 000 B — частями) → опрос `DocflowStatus`.

Результат — JSON в stdout, ход выполнения — в stderr:

```json
{
  "operationId": "…",
  "customDocumentId": "…",
  "fileName": "ON_NSCHFDOPPR_….xml",
  "fromBoxId": "…",
  "toBoxId": "…",
  "messageId": "…",
  "entityId": "…",
  "contentPlacement": "inline",
  "outcome": "success",
  "final": true,
  "status": { "…": "DocflowStatus из Диадока" },
  "polls": 2,
  "warnings": []
}
```

Опции:

| Опция             | Что делает                                                                                                                        |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `--no-precheck`   | Пропустить `CanPostMessage`.                                                                                                      |
| `--resend`        | Намеренно отправить тот же файл еще раз под новым `operationId` (случайная соль печатается в stderr и возвращается как `resend`). |
| `--resend=<соль>` | Повторить конкретную переотправку идемпотентно.                                                                                   |
| `-- <файл>`       | Имя файла, начинающееся с `-`.                                                                                                    |

Повторный `send` того же файла идемпотентен: `operationId` = SHA-256 от ящиков, `ИдФайл` и содержимого, и Диадок
возвращает уже созданное сообщение, новое не создается.

Коды выхода:

| Код     | Значение                                                                                                                                                                      |
| ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0       | Отправлено (статус успешный или еще в обработке).                                                                                                                             |
| 1       | Ошибка; stderr начинается с `error [КОД]` (`PIPELINE_CONFIG`, `SIGNER_CONFIG`, `DIADOC_CONFIG`, `DIADOC_AUTH`, `SIGN_FAILED`, `CERTIFICATE_INVALID`, `PRECHECK_REJECTED`, …). |
| 2       | Неверные аргументы.                                                                                                                                                           |
| 3       | Отправлено, но Диадок вернул ошибку документооборота или отклонил подпись отправителя (`docflow error [КОД]` в stderr, подробности в `signatureCheck`).                       |
| 4       | Отправлено, но в ответе нет сущности документа для отслеживания (`messageId` в stderr).                                                                                       |
| 130/143 | Второй Ctrl+C / SIGTERM: немедленный выход, в stderr — известный на этот момент `operationId`.                                                                                |

Первый Ctrl+C останавливает все шаги, кроме уже начатого `PostMessage` (он завершается в пределах 180 с).
Одновременно с одним refresh token запускайте только один процесс.

### Тестовая отправка без КЭП

Для проверки канала отправки на тестовых ящиках без собственной квалифицированной подписи:

```sh
SIGNER_KIND=diadoc-test npm run cli -- send utd/ON_NSCHFDOPPR_<...>.xml
```

Диадок подписывает документ своим тестовым сертификатом (`SignWithTestSignature`); стенд КриптоАРМ Server и
переменные `CRYPTOARM_*`/`SIGNER_CERT_PATH` при этом не нужны. Если хотя бы один ящик не тестовый, CLI отказывается
(`TEST_SIGNATURE_REFUSED`). Ожидаемый результат: код выхода 0, `"testSignature": true`, статус
«Ожидается подпись контрагента» — документ доставлен и ждет подписи покупателя.

> Подпись сертификатом тестового УЦ КриптоПро Диадок принимает (HTTP 200), но документ не доставляется:
> «Ошибка в подписи», цепочка не доверена → код выхода 3 `SENDER_CERTIFICATE_REJECTED`. Для реальной доставки
> нужен КЭП, выданный аккредитованным УЦ, — либо сертификат самого продавца, либо сертификат сотрудника с МЧД.

## CLI в Docker

```sh
npm run cli -- make-test-utd        # на хосте, до засева тома: в контейнере UTD_DIR только на чтение
docker compose build app

# один раз: положить refresh token во внешний том (переживает down -v).
# Нужны существующие UTD_DIR и .cer из SIGNER_CERT_PATH: compose монтирует их и без них не стартует.
docker volume create kryptoarm-diadoc-diadoc-token
docker compose run --rm -T --no-deps --entrypoint sh app \
  -c 'umask 077; cat > "$DIADOC_REFRESH_TOKEN_FILE"' < .diadoc-refresh-token

# подписать и отправить (стенд КриптоАРМ Server уже должен быть запущен и healthy);
# путь — относительно utd/, это рабочий каталог контейнера
docker compose run --rm --no-deps app send <ИдФайл>.xml
```

Контейнер читает корневой `.env`, обращается к серверу как `http://cryptoarm-server:3037`, монтирует
`SIGNER_CERT_PATH` и `UTD_DIR` только на чтение. Всегда используйте `--no-deps`: без него compose может пересоздать
общий стенд сервера.

> После засева в томе лежит **своя копия** refresh token. Если Диадок ротирует токен (в живых прогонах такого не
> было, но протокол это допускает), обновится только та копия, через которую шел запрос, а другая станет
> недействительной. Поэтому выберите одно место — хост (`.diadoc-refresh-token`) или том — и после засева удалите
> или не используйте другую копию. Если нужно снова работать с хоста, засейте том заново из актуального файла.

## Тесты

```sh
npm test                                              # юнит-тесты (HTTP замокан)
npm test -- src/pipeline/send.test.ts -t "<имя>"      # один тест
for t in scripts/test/*.test.sh; do "$t"; done        # shell-тесты стенда (фейки, без Docker)
```

Интеграционные — против запущенного стенда:

```sh
CRYPTOARM_SERVER_URL=http://127.0.0.1:3037 \
CRYPTOARM_SERVER_API_KEY="$(head -1 docker/cryptoarm-server/secrets/api_keys)" \
SIGNER_CERT_PATH=docker/cryptoarm-server/certs/cryptoarm.server.test.cer \
  npm test -- src/signer/server-cms-signer.integration.test.ts src/pipeline/signature-policy.integration.test.ts
```

Живой e2e с Диадоком (каждый кейс создает реальные документы на тестовых ящиках; выбирайте кейсы через `-t`):

```sh
DIADOC_E2E=1 DIADOC_E2E_ENV_FILE=.env DIADOC_REFRESH_TOKEN_FILE=.diadoc-refresh-token \
  npm test -- src/e2e/diadoc.e2e.test.ts -t 'test signature, inline'
```

Без `-t` запускаются все кейсы с тестовой подписью, включая загрузку 6,5 МБ на полку.

## Секреты

Лицензии, API-ключи, `client_secret`, `refresh_token`, контейнеры `.pfx` и PIN-коды хранятся только в
git-ignored файлах: `.env`, `.diadoc-refresh-token`, `docker/cryptoarm-server/.env`,
`docker/cryptoarm-server/secrets/`. В репозитории — только `.env.example` с заглушками.

## Структура

| Путь                      | Что там                                                                     |
| ------------------------- | --------------------------------------------------------------------------- |
| `src/cli.ts`              | CLI: `send` и `make-test-utd`                                               |
| `src/pipeline`            | `sendUtd`: разбор → подпись → проверка → отправка → опрос статуса           |
| `src/signer`              | `ServerCmsSigner` — клиент КриптоАРМ Server                                 |
| `src/diadoc`              | OIDC-авторизация (refresh token) и клиент API Диадока                       |
| `src/utd`                 | разбор УПД, формирование вложения, генератор тестового УПД                  |
| `src/asn1`                | BER → DER, разбор CMS и сертификатов для политики подписи                   |
| `docker/cryptoarm-server` | стенд КриптоАРМ Server                                                      |
| `scripts/`                | тестовые сертификаты, выпуск сертификата в тестовом УЦ, smoke-тест сервера  |
| `docs/`                   | план задач (`plan.md`), исследования и живые прогоны (`research.md`), ревью |

## Ограничения PoC

- Тестовые сертификаты и корень тестового УЦ КриптоПро действуют до **2026-10-28**.
- Политика подписи не сверяет организацию в сертификате с продавцом в УПД; Диадок в этом случае только
  предупреждает о МЧД.
- Максимальный размер подписываемого файла ≈ 39,3 МБ (лимит тела запроса КриптоАРМ Server).
