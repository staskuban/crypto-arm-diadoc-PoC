## КриптоАРМ Server (`git.digtlab.ru/trusted/cryptoarm/server`, v1.4.25)

- `POST /cms/sign` DTO (`src/controllers/dto/cms.dto.ts`): `cert`, `data`, `password`, `detached` (default **true**), `cadesStandard` (`CAdES-BES` default; `-T`, `-X Long Type 1`, `-A` need a TSP URL), `tspServiceAddress`.
- Service (`src/services/cms.service.ts`): `applySignedDataCryptoSignOptions(cms, detached !== false, ...)` → `cms.policies = ['detached']`.
- Key lookup (`src/services/cert-store.helper.ts` `resolveSigningCertificate`): PKCS#12 → temporary install into `uMy`; plain X.509 → find the private key in the store by thumbprint. So keys can be installed once at container start and clients send only the public `.cer`. Our stand's entrypoint (`docker/cryptoarm-server/start.sh`, I5) installs `*.pfx`/`*.p12` from `/certs/user` and `secrets/` (PIN, if any, from the sibling `<name>.pfx.pin`; by README convention `certs/user` holds PIN-less test containers), and legacy `CERT_PFX_BASE64`/`CERT_PFX_PIN` (test keys only: env is readable via `docker inspect`); `scripts/issue-test-cert.sh` (I3) instead generates the key inside the container.
- `/cms/sign` returns the CMS as **BER with indefinite lengths** (`30 80 …`), not strict DER (verified on the I1 stand, 2026-09-24). Since F2 `ServerCmsSigner` normalises it to DER (`src/asn1`), so Диадок always gets DER. `/cms/verify` answers a data mismatch with `201 {isValidSign:false}`, not a 4xx.
- **Request body limit** (T10, measured on the shared stand 2026-09-24, `JSON_LIMIT=50mb`): exactly **52 428 800 B** (50 MiB) of JSON body is parsed, 52 428 801 B is rejected by body-parser before the handler — with **HTTP 400** `{"statusCode":400,"message":"request entity too large"}`, not 413 (same on `/cms/sign` and `/cms/verify`; D30). Data travels as Base64 inside the JSON and the verify body also carries the Base64 CMS, so the largest signable+verifiable file is ≈ ¾ of the limit minus a few KB: 39 272 448 B signed and verified in ~8 s; 3.5 MB in < 1 s. `ServerCmsSigner` refuses a body over `maxRequestBytes` (default 52 428 800, env `CRYPTOARM_SERVER_MAX_REQUEST_BYTES`, keep equal to `JSON_LIMIT`) before encoding and maps the server's 400/413 «too large» to `SignerPayloadTooLargeError`; pinned in `src/signer/server-cms-signer.integration.test.ts`.
- Build: upstream builds from its `docker/Dockerfile`; our stand builds `docker/cryptoarm-server/Dockerfile` locally (upstream base image pinned by digest, I5). Requires a human-downloaded КриптоПро CSP 5.0 `linux-amd64_deb.tgz` and a valid `TRUSTED_LICENSE` — without it the server exits `Trusted Crypto license is invalid` (restart loop; verified 2026-09-24). `CRYPTOPRO_LICENSE` is optional: empty = CSP Demo trial (~90 days from the first start of a fresh `cert_storage/`). x86_64 only. Licences and `API_KEYS` come from `secrets/<var>` files since I5 (env is the legacy path).
- Test material in repo: `certs/crypto.root.test.cer`, `certs/cryptoarm.server.test.{cer,pfx}` (CRYPTO-PRO Test Center 2).

- Repo `trusted/cryptoarm/documents/api` contains only `docker/`, `docs/`, `.env.example` — the service code is closed, but the API image ships its TypeScript sources next to `dist/` (e.g. `/modules/signatures/signatures.service.ts`, `/auth/auth.service.ts`; `dist` matches them). The findings below come from those sources **and** live runs on the I2 stand (`docker/cryptoarm-documents`, 2026-09-24, image `api:1.0.209` reporting 1.0.211, test licence product `CD1`).
- Images `registry.digtlab.ru/trusted/cryptoarm/documents/{api,app}` pull anonymously (tags `1.0.143`, `1.0.196`, `1.0.209`, `latest`; single-arch amd64). Needs `LICENSE_VALUE` (without it the API does not start), a DB (`DB_URI`, sqlite or postgres), `SIGN_SERVICE_URL` → КриптоАРМ Server. An OIDC IdP is **not** required: with `OAUTH2_ENABLED` unset/false the API creates a local admin (`ADMIN_LOGIN`/`ADMIN_PASSWORD`/`ADMIN_EMAIL`) and accepts `POST /api/v1/login`.
- **How `cloud-sign` selects the key** (answer to the I2 question): `POST /api/v1/signatures/cloud-sign/{documentId}` `{pin?}` takes the logged-in user's **e-mail**, fetches `GET {CA_API_URI}/cert/{email}?format=pfx` (`x-api-key: $CA_API_TOKEN` if set; JSON `pfx|cert|data` or the raw body, base64) and posts it as `cert` (and `pin` as `password`) to `{SIGN_SERVICE_URL}/cms/sign` with `X-API-Key: $SIGN_SERVICE_API_KEY`, without `detached`/`cadesStandard` → server defaults (detached `CAdES-BES`). `corpCloudCertAvailable` in the profile = `GET {CA_API_URI}/cert/{email}/exists` → `{exists, has_pfx, has_private_key}`. No other setting, no per-request choice. The "CA API" is an external service not shipped with Документы; the I2 stand replaces it with an nginx stub that maps e-mail → **public `.cer`**, and КриптоАРМ Server finds the key already in `uMy` by thumbprint (verified with `cryptoarm.server.test.cer` and `o2-platforma.test.cer`, thumbprints reported by the verification match). So on our side the signer choice = which Документы user calls `cloud-sign` + the e-mail → certificate mapping of the CA service.
- `SIGN_METHOD_CORP_CLOUD` only toggles the method in `/api/v1/profile` (UI); `cloud-sign` signs with it `false` too (verified). `cloud-sign` has **no document access check**: a user who gets `403` on `GET /api/v1/documents/{id}` can cloud-sign that document (verified). A user may sign a document once (`400 "Повторная подпись документа этим пользователем запрещена"`). Unmapped e-mail → `400 "Не удалось получить корпоративный сертификат пользователя"`. Cloud signing did not consume `availableSignatureLicenses` (10 → 10).
- Auth (verified): the global `X-API-KEY` is disabled in this version (any key → `401 "API Key is wrong"`); working options are the session cookie of `POST /api/v1/login` (by `login`, not e-mail) and `Authorization: Bearer` with the JWT from `GET /api/v1/auth/jwt?expiresIn=` (≤ `API_JWT_TOKEN_EXPIRES_MAX`, default 90d). Any HS256 token signed with `MAIL_LINK_TOKEN_SECRET` is accepted for **any** e-mail and auto-registers it (`ALLOW_REGISTRATION` default true; image default secret `change-me`) — together with the e-mail-based key choice this secret is equivalent to the signing keys.
- `POST /api/v1/signatures` only stores an external signature. Detached export: `POST /api/v1/documents/{id}/signature {signatureId, attached:false}` → the stored CMS bytes as is: the server's **BER, indefinite length** (`30 80`), detached, identical to `cloud-sign`'s `signature` (base64). A Диадок client must convert it to DER (`src/asn1`).
- `POST /api/v1/documents/{id}/verify` returns a **PDF** report, not JSON. The machine-readable result is the signature `meta` from `GET /api/v1/signatures?filter={"documentId":id}` (`signValid`, `signers[].certificate.thumbprint`, `isCertChainValid`, `isDetached`, `cadesTypeName`), filled by the server's `/cms/verify` when the signature is stored (`VERIFY_SIGNATURE_AFTER_RECEIVE`, default on; a failed check deletes the signature and fails `cloud-sign`).
- Upload keeps the bytes (download identical for a windows-1251 УПД); the part's MIME type must match `ALLOWED_FILE_TYPES` (upstream default has no `xml`).
- **Size limits and idempotency (F14, measured on the shared I2 stand 2026-09-24, image `api:1.0.209`, plus the API sources shipped in the image):**
  - Upload: `MAX_FILE_SIZE=50` is MiB. Multer's `fileSize` limit is 52 428 800 B; the largest accepted file is **52 428 799 B**, a file of 52 428 800 B gets **HTTP 413** `{"error":{"code":"bad_request","message":"File too large"}}` (binary search, text/plain part). A separate pre-check middleware answers 413 «Файл слишком большой. Максимальный размер: 50 МБ» with `details.maxFileSizeBytes` when `Content-Length` > 50 MiB + 256 KiB (not hit by Node's `FormData` upload).
  - `cloud-sign` posts `{cert, data[, password]}` (Base64) to КриптоАРМ Server `/cms/sign` and turns **any** non-2xx answer into **HTTP 400** «Ошибка облачной подписи: <server message>» (wrong-PIN texts become «Неверный PIN-код…»). Over `JSON_LIMIT` it is `400 "Ошибка облачной подписи: request entity too large"`. The largest file `cloud-sign` signs is **39 319 329 B** (Base64 52 425 772 B + ≈ 3 KB of `cert`); 39 319 332 B fails. With the default limits the verify body (next item) is the binding limit, not the 50 MiB upload.
  - `DocumentsCloudSigner` now refuses data whose `/cms/verify` body (Base64 of the data + Base64 of a 16 KiB signature margin + 20 B) exceeds the verifier's `maxRequestBytes`: with 52 428 800 B that is files above **39 305 199 B**, about 14 KB less than `cloud-sign` could sign (the real CMS is ≈ 2.2 KB).
  - Idempotency (`middleware/idempotency.middleware.ts`, `modules/idempotency/idempotency.service.ts`): an in-memory map per API process (lost on restart, TTL `IDEMPOTENCY_TTL_MS`, default 24 h), keyed by key + method + path + SHA-256 of the JSON body + user; multipart requests are skipped (so the upload ignores the key, D15). Only answers with status **< 500** are stored: a **5xx is not cached** and a repeat runs the handler again. Nothing marks a key as in flight either. Live: a 400 over `JSON_LIMIT` repeated with the same key came back from the cache in 12 ms with `Idempotency-Replayed: true` (a new key ran it again, ≈ 0.6 s); two concurrent `cloud-sign` calls with one key on a fresh document gave one `200` and one `400 "Повторная подпись документа этим пользователем запрещена"`, and a third call replayed the `200` (the cache keeps whichever answer was written last). So a repeat after our timeout, or after a 5xx that came after the signature was stored, ends in that 400; `DocumentsCloudSigner` adds a hint to it (each signing uploads a new document, so only our own earlier attempt can have signed it).
  - `cloud-sign` stores the signature, then verifies it (`checkSignature`) and deletes it if that throws; a relayed «Закрытый ключ … не найден» of the server therefore arrives as a 400 (matched by `SignerKeyNotFoundError`), not a 5xx (source only, not reproduced: the stand maps every e-mail it knows to a key).
