### S1 spike findings (2026-09-24, scripts in `spikes/diadoc/`)

Endpoints and headers. Everything comes from `authentication.html`, `howtostart/integration.html` and `http/<Method>.html` / `proto/*.html` on developer.kontur.ru. **Live-checked** (fake credentials, 2026-09-24): the token endpoint and its `invalid_client` error, the OIDC discovery scopes, the staging host with `401` on a missing or bad token for `GetMyOrganizations` and `V3/GetDocumentTypes`, and `405` on `GET /V3/PostMessage`. Everything else is **documentation only** until a run with real credentials:

| Step | Request | Notes |
|---|---|---|
| Token | `POST https://identity.kontur.ru/connect/token`, `Content-Type: application/x-www-form-urlencoded`, body `grant_type=refresh_token&client_id=…&client_secret=…&refresh_token=…` | One IdP for prod and staging. No `scope` in the refresh request: the scope (`Diadoc.PublicAPI.Staging`, listed in `/.well-known/openid-configuration`) is set when the refresh token is issued in the integrator cabinet. Documented response `{access_token, token_type: "Bearer", expires_in: 86400, refresh_token}`. The docs contradict each other: one section says the refresh token is rotated on each refresh and the new one must be stored; another says the cabinet-issued token stays valid until it is revoked (30-day sliding lifetime). Store the returned token anyway. A bad client gets `400 {"error":"invalid_client"}` (checked live). |
| API hosts | prod `https://diadoc-api.kontur.ru`, staging `https://diadoc-api-staging.kontur.ru` | `Authorization: Bearer <access_token>`, `Accept: application/json`. A missing or bad token gets `401` with `text/plain` "Invalid auth token" (checked live). Box ids differ between prod and staging (`403` if mixed). |
| Orgs | `GET /GetMyOrganizations?autoRegister=false` | `Organizations[].{Inn, Kpp, FnsParticipantId, Boxes[].{BoxId "<hex>@diadoc.ru", BoxIdGuid}}`. `autoRegister` defaults to true, which may register the user into an org (limit 3 per day, then `409`). |
| Org by box | `GET /GetOrganization?boxId=<guid>` | Source of seller/buyer INN/KPP/`FnsParticipantId` for the УПД. |
| Types | `GET /V3/GetDocumentTypes?boxId=<guid>` | `DocumentTypes[Name=UniversalTransferDocument].Functions[].Versions[].{Version, Titles[].{XsdUrl, UserDataXsdUrl, SignerInfo, MetadataItems}}`. |
| Pre-check | `POST /CanPostMessage` JSON `{FromBoxId, ToBoxId, DocumentPrototypes[{CustomDocumentId, TypeNamedId, Function, Version}]}` | Returns `MessageValidationResult {Errors[{Severity, UserMessage, ApiMessage, CustomDocumentId}]}`. Checks boxes and types only, not content or signature. |
| Send | `POST /V3/PostMessage?operationId=<id>` JSON `MessageToPost` | Idempotent per `operationId` (default: MD5 of the body). `204` + `Retry-After` means still processing, so repeat the same call. `409` means a duplicate, or the recipient's `Sociability` forbids it. The file name comes back in `Content-Disposition`. |

УПД file (приказ 970 §4, checked against the КонсультантПлюс text and the Диадок sample): `ON_NSCHFDOPPR_<recipient FnsParticipantId>_<sender FnsParticipantId>_<YYYYMMDD>_<GUID>_<N2>_<N3>_<N4>_<N5>_<N6>_<N7>`. The flags N2–N6 mark traceable, marked, alcohol, tobacco and oil goods. N7 is a two-digit reserve. For plain goods the tail is `_0_0_0_0_0_00`. The spike builds a minimal `СЧФДОП` (1 line, 22% VAT, `БезДокОснПер`, `Подписант СпосПодтПолном="1"`) as windows-1251 bytes. It validates against `ON_NSCHFDOPPR_1_997_01_05_03_05.xsd` with `xmllint`. The Schematron rules embedded in the same XSD (`xs:appinfo/sch:pattern`: file name == `@ИдФайл`, and `СвПродПер`/`НаимДокОпр`/`Адрес`/`ДатаПер` required for `СЧФДОП`) were checked by hand, because xmllint does not run them. `СпосПодтПолном` values: 3 needs `СвДоверЭл` (МЧД), 5 needs `СвДоверБум`, 1 and 6 need neither.

**Still open: are test-CA signatures accepted?** Neither the docs nor a web search say whether the staging platform accepts a CMS from a КриптоПро test-CA certificate. `SignWithTestSignature` exists because test boxes have no qualified certificates. Hypothesis: the CMS will parse and verify against the content, but the certificate checks may fail. Those checks are chain trust (a non-accredited CA) and, for УПД titles, whether the owner matches the sender org and the `Подписант`. The upstream test certificate `cryptoarm.server.test` carries no org INN. I3 (2026-09-24) added a test-CA certificate `o2-platforma.test.cer` for ООО «О2 ПЛАТФОРМА» with ИНН ЮЛ `1.2.643.100.4`=2311386400 and ОГРН `1.2.643.100.1`=1252300058977 (the test CA kept both), so the owner check can be tried with a matching org; the signer person in it is a placeholder, so a `Подписант` name check would still fail. Answering this needs a live run: `post --test-signature` first (proves auth, boxes and XML), then `post --signature` with a КриптоАРМ Server CMS (needs I1), then `status` → `DocflowStatus` and any `PostMessage` 4xx text. If staging rejects it, the options are (a) `SignWithTestSignature` on staging for T6 plus a real КЭП on prod for the signature path, or (b) asking Диадок support to trust the test CA for our test boxes.

## КриптоАРМ Server (`git.digtlab.ru/trusted/cryptoarm/server`, v1.4.25)

- `POST /cms/sign` DTO (`src/controllers/dto/cms.dto.ts`): `cert`, `data`, `password`, `detached` (default **true**), `cadesStandard` (`CAdES-BES` default; `-T`, `-X Long Type 1`, `-A` need a TSP URL), `tspServiceAddress`.
- Service (`src/services/cms.service.ts`): `applySignedDataCryptoSignOptions(cms, detached !== false, ...)` → `cms.policies = ['detached']`.
- Key lookup (`src/services/cert-store.helper.ts` `resolveSigningCertificate`): PKCS#12 → temporary install into `uMy`; plain X.509 → find the private key in the store by thumbprint. So keys can be installed once at container start (`/certs/user/*.pfx` or `CERT_PFX_BASE64`/`CERT_PFX_PIN`) and clients send only the public `.cer`.
- `/cms/sign` returns the CMS as **BER with indefinite lengths** (`30 80 …`), not strict DER (verified on the I1 stand, 2026-09-24). `ServerCmsSigner` accepts it as is; whether Диадок accepts BER in `Signature` is checked in S1/T6. `/cms/verify` answers a data mismatch with `201 {isValidSign:false}`, not a 4xx.
- Build: image built locally from `docker/Dockerfile`; requires human-downloaded КриптоПро CSP 5.0 `linux-amd64_deb.tgz`, `TRUSTED_LICENSE`, `CRYPTOPRO_LICENSE`; x86_64 only.
- Test material in repo: `certs/crypto.root.test.cer`, `certs/cryptoarm.server.test.{cer,pfx}` (CRYPTO-PRO Test Center 2).

## КриптоАРМ Документы

- Repo `trusted/cryptoarm/documents/api` contains only `docker/`, `docs/`, `.env.example` — service code is closed.
- Images `registry.digtlab.ru/trusted/cryptoarm/documents/{api,app}` pull anonymously (tags `1.0.143`, `1.0.196`, `1.0.209`, `latest`; single-arch manifest).
- Requires `LICENSE_VALUE`, OIDC IdP (docs say КриптоАРМ ID is mandatory; `.env.example` hints at local login with `OAUTH2_ENABLED=false` — contradictory), `SIGN_SERVICE_URL` → КриптоАРМ Server.
- `POST /api/signatures` only stores an external signature. Server-side signing: `cloud-sign` (`SIGN_METHOD_CORP_CLOUD`, default false) and `dss-sign`. User docs describe only desktop КриптоАРМ, upload and Госключ; how `cloud-sign` selects the corporate key is undocumented.
- Detached signature export: `POST /api/documents/{id}/signature { signatureId, attached: false }`.
- **Blocked:** no `LICENSE_VALUE` yet → Документы are off the critical path (see `docs/plan.md`).
