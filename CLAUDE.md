## Goal

Automated pipeline for УПД (universal transfer document, ФНС format):
1. Centrally store signing keys/certificates and signing tools in **КриптоАРМ**.
2. Sign УПД documents automatically via the КриптоАРМ Server public API.
3. Send the signed documents to counterparties via **Контур.Диадок** public API.

**Signing path (decided 2026-09-24, КриптоАРМ Server only since F21):** КриптоАРМ Server holds the private keys and signs via `POST /cms/sign`; the pipeline depends on a `Signer` interface with one implementation, `ServerCmsSigner`. КриптоАРМ Документы are not part of the project (removed in F21 after C1, see `docs/compare-documents.md`).

Only public APIs of both systems are used. No database — КриптоАРМ Server holds the keys, Диадок the state (messages, docflow status).

## Development workflow (Orca worktrees)

Mandatory process for any multi-task work:
1. **Map dependencies first.** Before splitting into subtasks, identify all links between them (which task consumes interfaces/types/fixtures of another) and build a DAG.
2. **One worktree per subtask**, created via the `orca-cli` skill. Independent tasks run in parallel.
3. **Dependent worktrees get the dependency as parent**: a child worktree branches from its parent's worktree/branch, not from `master`.
4. **After each task completes**: merge it into its parent, then run integration tests on the parent.
5. **If integration breaks**: fix it in a **separate new worktree** (child of the broken parent), not by patching inside the finished task's worktree.
6. **Naming**: every task worktree name/display name starts with its task code from `docs/plan.md` (e.g. `T2-signer`, `I1-infra-server`).
7. **Board status**: when a task is finished (report written, `docs/plan.md` status updated), move its worktree to `in-review` on the Orca workspace board: `orca worktree set --worktree active --workspace-status in-review --json`.

Git: default branch is `master` (not `main`). The stash stack is shared across worktrees — never use bare `git stash`/`git stash pop`.

## External systems

### КриптоАРМ Server (self-hosted crypto backend, docker compose)
- Repo & install guide: https://git.digtlab.ru/trusted/cryptoarm/server (compose file, Dockerfile, `.env` are fetched from `docker/` in that repo).
- Default port `3037`, Swagger at `/docs`. Auth via `AUTH_MODE=none|apikey` + `API_KEYS`; key passed as `X-API-Key`, `Authorization: Bearer`, or `?apiKey=`. Upstream compares `AUTH_MODE` literally: `apikey` without keys rejects everything, any other value (`APIKEY`, empty) or a missing variable accepts everything without a key (D160) — `start.sh` refuses all of these (F16).
- Body limit (T10, measured): `JSON_LIMIT=50mb` = exactly 52 428 800 B of JSON body; one byte more → **HTTP 400** «request entity too large» (not 413, D30). Base64 + the CMS in the verify body → largest file ≈ 39.3 MB (39 272 448 B signed + verified in ~8 s). `ServerCmsSigner` checks `maxRequestBytes` (default 52 428 800, env `CRYPTOARM_SERVER_MAX_REQUEST_BYTES`, keep equal to `JSON_LIMIT`) before encoding and throws `SignerPayloadTooLargeError` (also for the server's 400/413 «too large»).
- Signing: `POST /cms/sign` with `{ cert, data, password?, detached?, cadesStandard? }` (Base64) → `{ cms }`. `detached` defaults to **true**, `cadesStandard` to `CAdES-BES`. The `cms` is **BER with indefinite lengths**; `ServerCmsSigner` normalizes it to DER (`src/asn1`), keeping the raw bytes as `rawSignature`. A `.cer` whose key is not in `uMy` → 400 «Закрытый ключ … не найден» → `SignerKeyNotFoundError`. Also `/cms/verify`, `/cert/verify`, `/hash`, `/cms/attached-to-detached`.
- Keys stay on the server: install PFX at container start (`/certs/user/*.pfx` without PIN, `secrets/*.pfx` + `secrets/<name>.pfx.pin`; `CERT_PFX_BASE64` + `CERT_PFX_PIN` only for test keys; roots in `/certs/root`), then pass only the public `.cer` as `cert` — the key is found in `uMy` by thumbprint. Passing a `.pfx` also works but installs it temporarily per request. Test cert/key from CRYPTO-PRO Test Center 2 ship in the upstream repo `certs/`.
- Stand hardening (I5): base image pinned `server:1.4.25@sha256:065293ad…`; entrypoint `docker/cryptoarm-server/start.sh` (exec form under `init`) reads `TRUSTED_LICENSE`, `CRYPTOPRO_*LICENSE`, `API_KEYS` from `<VAR>_FILE` → `docker/cryptoarm-server/secrets/<var>` (git-ignored, mounted read-only at `/run/secrets`) → env (legacy); logs `certmgr` failures (PIN redacted) and continues; F16: `API_KEYS` split on newlines/commas, trimmed, empty dropped (a key with inner whitespace stops the start), `AUTH_MODE` must be set: `apikey` with ≥ 1 key or `none` (warned), licence-tool output logged with the licence redacted; `cap_drop: [ALL]` + `no-new-privileges` (enough on Docker Desktop; a Linux host needs root-owned files or `DAC_READ_SEARCH`); I6: `read_only` rootfs + tmpfs (`/etc/opt/cprocsp` seeded by `start.sh` from the image, `/etc/opt/Trusted`, `/var/lib/cryptoarm-server` for `cash.json`, `/tmp`, fontconfig cache) and `CRYPTOARM_SERVER_CPUS/MEMORY/PIDS` limits (2 / 2g / 256) — the compose file needs the I6 image, an older one is `unhealthy` (D40), so its default tag is `…:stand-i6` (F10: with only an older image `up` fails with "No such image" and keeps the running container; rollout/rollback for the shared stands in the stand READMEs); `LOG_LEVEL=warn,error` (the `log` level prints API key prefixes). CSP licenses and PINs still pass through argv of the CSP tools at start (no other input).
- Licenses: `CRYPTOPRO_LICENSE` may be empty (CSP Demo trial). `TRUSTED_LICENSE` is **required** — without it the server exits `Trusted Crypto license is invalid` (verified 2026-09-24). Keep real licenses only in untracked files (`secrets/`, or the legacy `.env`).
- **Manual prerequisites**: КриптоПро CSP 5.0 `linux-amd64_deb.tgz` downloaded by a human (cryptopro.ru login) into `docker/cryptoarm-server/cryptopro/`, and a `TRUSTED_LICENSE` key. Image is x86_64 only — on Apple Silicon it runs under emulation (build ~30 s once the base image is cached).
- Test cert `CN=cryptoarm.server.test` and its CA root expire **2026-10-28** — and so does every cert the test CA issues now (capped by its current CA cert, renewal 21).
- Signer cert of ООО «О2 ПЛАТФОРМА» (ИНН ЮЛ/ОГРН honoured by the test CA, placeholder signer person): `scripts/issue-test-cert.sh` generates a PIN-less non-exportable key inside the running container (its files live on the host in the bind-mounted `cert_storage/`, protected only by file permissions — test keys only), enrolls at http://testgost2012.cryptopro.ru/certsrv/, binds it in `uMy` and writes only `docker/cryptoarm-server/certs/o2-platforma.test.cer` (+ issuer in `certs/root/`). Refuses an existing `KEY_CONTAINER`, a failing `csptest -enum_cont` (R2 M3) and a name another run holds (`/tmp/<name>.lock` in the container); the AIA issuer must be in the SHA-256 allowlist `scripts/test-ca-roots.sha256` (shared with `fetch-test-certs.sh`). After the CA rolls its key: check the new root out of band, add its hash, re-run. Details: `docker/cryptoarm-server/README.md`.
- Upstream `crypto.root.test.cer` is byte-identical to the leaf and does not work as a root: `/cms/verify` then returns `isValidSign=false` (chain), so `scripts/fetch-test-certs.sh` installs the real test CA root from the cert's AIA URL instead. `isValidSign` includes the chain; the pure math result is `signs[].extVerifyInfo.mathValidity`.

### Контур.Диадок API
- Docs: https://developer.kontur.ru/doc/diadoc-api/index.html (has an OpenAPI spec and SDKs linked from there).
- Auth: OIDC access token via **Refresh Token Flow** — `client_id`, `client_secret` (= API key from «Кабинет интегратора») and a `refresh_token` issued once in the integrator cabinet; refresh `access_token` automatically. Use a service account with rights to create and sign documents.
- Test space: two test boxes created via the quickstart form (`diadoc.kontur.ru/easyregistration`) and added as counteragents to each other. They are `IsTest` organisations on the **production** host `https://diadoc-api.kontur.ru` — use that host with them, not staging: `diadoc-api-staging.kontur.ru` (OIDC scope `Diadoc.PublicAPI.Staging`) does not know them (404, D191). The same refresh token works on both hosts; `.env.example` defaults to the production host.
- Sending: `PostMessage (V3)` with `MessageToPost { FromBoxId, ToBoxId, DocumentAttachments[] }`, each attachment has `TypeNamedId`, `Function`, `Version` and `SignedContent { Content, Signature }`. `Signature` is CMS SignedData in DER, separate from `Content` (i.e. **detached**; the official C# SDK signs with detached=true). `Content` inline only if < 500 KB (the pipeline cuts at 500 000 B; live, 510 185 B inline were still accepted, D220), otherwise `ShelfUpload` + `NameOnShelf`; 70 MB per request. Pre-check with `CanPostMessage` (requires a GUID `CustomDocumentId` per prototype, D200/D192). Status via `GetDocument` → `DocflowStatus`; the reason of a signature error via `SenderSignatureStatus`, `GetSignatureInfo` and the `DeliveryFailureNotification` entity of `V5/GetMessage` (D203). `SignWithTestSignature` exists for test runs.
- УПД (verified): `TypeNamedId = "UniversalTransferDocument"`, `Function` ∈ `СЧФ | ДОП | СЧФДОП | СвРК | СвЗК`, `Version = utd970_05_03_01` (`utd970_05_02_01` is obsolete). Take values from `GetDocumentTypes (V3)` and tolerate unknown versions. The ФНС XSD is `windows-1251` and requires file name == `@ИдФайл` — sign and send the exact same bytes, never re-encode. Signer block (universal format) must be filled **before** signing.
- Pipeline decisions (T5, T8): `operationId` = SHA-256 over boxes + `ИдФайл` (not the file name, so `.xml`/`.XML` is one send) + content + `customDocumentId` (only when given) + optional resend salt (not the signature, which changes on re-signing), so re-running `send` for the same file sends the same `operationId`; Диадок replays the original message (same `MessageId`, old status) for a different body and creates nothing new (live, S1/D7), so a re-signed send after an error needs `--resend`; a `400` is not cached: the same `operationId` with a fixed body posts a new message (live, T6, D221). A deliberate resend (`SendUtdOptions.resend` / CLI `--resend[=<salt>]`) changes only the salt. `CustomDocumentId` (F19, D200): every attachment and the `CanPostMessage` prototype carry one; `SendUtdOptions.customDocumentId` must be a canonical GUID (else `sendUtd` throws before signing, D192), without it a GUID is derived from the `operationId` (`customDocumentIdFor`, RFC 9562 v8 over SHA-256: a retry keeps it, a resend gets a new one; accepted by `CanPostMessage` live; `PostMessage` accepts the v8 GUID and `GetDocument` echoes it (live, T6, D211); `PostMessage` itself also accepts a non-GUID id, only `CanPostMessage` refuses it (D222)); it is returned as `customDocumentId`. After polling, an error status or `SenderSignatureStatus: SenderSignatureCheckedAndInvalid` triggers `checkSenderSignature` (`src/pipeline/signature-check.ts`: `V5/GetMessage` + `GetSignatureInfo` of the first Signature under the document, own soft 90 s deadline — above the IdP's 30 s so a token refresh can still start; each request keeps its own timeout — never throws; the sender signature is the one whose `SignerBoxId` is the sender box, else the first under the document): `signatureCheck { reason: certificate | signature | none | unknown, mathValid, certificateValid, chainProblems (CryptoAPI `CERT_TRUST_*` names), certificate, delivered: false + deliveryFailure text, powerOfAttorney, lookupErrors }`, pinned on the recorded S1 answers in `src/pipeline/fixtures/diadoc-s1/`. `409` texts are classified only in `src/pipeline/conflict.ts` (unverified, D4). Content ≥ 500 000 B goes to the shelf: `V2/ShelfUpload` up to 3 000 000 B, above that `ShelfUploadPartInit` + `ShelfUploadPart` in 3 000 000 B parts (re-sends the parts the last answer lists as missing, ≤ 2 re-sends like the C# SDK; each request has the F3 retry); above 400 000 000 B → `CONTENT_TOO_LARGE` before parsing. Shelf contract live-verified in T6 (D223): `V2/ShelfUpload?fileExtension=` and `ShelfUploadPartInit?fileExtension=&isLastPart=` answer the name as text, `ShelfUploadPart?fileName=&partIndex=&isLastPart=` answers the last part with a JSON array of missing indexes (`[1]`), a missing middle part re-sent with `isLastPart=true` answers `[]` and the stored file is byte-identical (D14 closed). 400 MB is the shelf's limit, not a tested end-to-end one: the signer path sends the whole file base64 in JSON twice (`/cms/sign`, `/cms/verify`) and `parseUtd` decodes it to a string — so the real ceiling is the КриптоАРМ Server body limit (T10, below): data above ≈ 39.3 MB fails with `SignerPayloadTooLargeError` as `SIGN_FAILED` (or `VERIFY_FAILED` in a few-KB window where only the verify body is over), not `CONTENT_TOO_LARGE` (D31). Status polling never throws after a successful post: it returns `outcome` `success | error | pending` with the ids.
- Диадок HTTP (F3): no redirects are followed (`redirect: 'error'`, API and IdP). Every Диадок and IdP request repeats the identical request on 429 (honouring `Retry-After`; longer than the budget → give up), 408, 500/502/503/504, network errors and timeouts — 4 attempts, ≤ 120 s of pauses per call (`src/diadoc/http-retry.ts`); PostMessage keeps the serialized body and `operationId`. A PostMessage failure after a request with unknown outcome is `DiadocPostOutcomeUnknownError` → `POST_FAILED` "may have been posted"; a request that never connected (`ECONNREFUSED`, `ENOTFOUND`, `EAI_AGAIN`, undici connect timeout; not `EHOSTUNREACH`/`ENETUNREACH`, which can hit a reused socket) does not count (F11). The refresh-token file (`src/diadoc/token-file.ts`) is locked via `<file>.lock` (O_EXCL) for the whole CLI run (it records pid/host/time; after a kill -9 or a `docker stop` past its grace period it stays and must be removed by hand, see `.env.example`), must not be a symlink or a mount point of its own (`st_dev` differs from its directory's, e.g. a single-file bind mount: `rename` would fail only at the first rotation; a heuristic — a bind mount of a file from the same file system as its directory's mount is not caught), and is replaced via a fresh `<file>.tmp` (0600, fsync, rename, dir fsync; a failing dir fsync only warns; a `<file>.tmp` found at start is warned about, it may hold a newer token). Shutdown budget (F11, R2 M2): PostMessage has one wall-clock budget `POST_MESSAGE_BUDGET_MS` = 180 s (`src/diadoc/client.ts`) for its `204` rounds, retries, pauses, token refreshes and each request's timeout; a `204` without `Retry-After` waits 5 s (`POST_PENDING_FALLBACK_MS`); a retry or `204` round only starts with ≥ 5 s left (`POST_MIN_REQUEST_MS`), else the last answer stands (`204` → `POST_PENDING`, 429 → `POST_FAILED` 429, 5xx → "may have been posted"). The first Ctrl+C/SIGTERM stops everything else at once (signer, CanPostMessage, shelf upload, token refresh, polling) and lets a running PostMessage finish; `stop_grace_period: 200s` on the compose `app` service covers that (checked by `src/cli.test.ts`). The second signal exits at once (128 + signal): it removes `<file>.lock` synchronously and prints the `operationId` (and `messageId`) known so far, plus a pointer to `<file>.tmp` if a rotated token was being saved. `docker stop` sends only one SIGTERM; a second one needs Ctrl+C or `docker kill -s TERM`. A token refresh inside an API call honours that call's deadline and abort signal only before and between token requests: a request is started only if its full IdP timeout (30 s) ends before the deadline (so a refresh needed in the last 30 s of polling fails as a status error), a sent token request is never cut (its answer may rotate the refresh token, which then still reaches the disk). No `expires_in` → 5 min lifetime, more than a day is cut to a day; the token is renewed `min(60 s, expires_in / 2)` before it expires (F12). The IdP keeps its own 30 s request timeout: `DIADOC_TIMEOUT_MS` applies to Диадок API requests only (D-6, a longer IdP timeout would keep a refresh from starting inside the PostMessage budget). Token errors (F12): a non-2xx names the status and the OAuth answer (+ a hint: `invalid_grant` → issue a new refresh token in the integrator cabinet, a left-over `<file>.tmp` may hold a newer one; `invalid_client` → check `DIADOC_CLIENT_ID`/`SECRET`, and since F19 also names an invalid/expired/revoked refresh token, because `identity.kontur.ru` answers a bad refresh token with `invalid_client`, not `invalid_grant` (D190)); a non-JSON 2xx names only status, content type and length (it may carry tokens); the token URL is printed as origin + path only, and the client secret and refresh token are cut out of an echoed body. In the pipeline any `DiadocAuthError` (also as a `cause`) is `DIADOC_AUTH` with the step where it happened (precheck, upload, post; exit 1), except after a PostMessage request with unknown outcome, which stays `POST_FAILED` "may have been posted", and except `DiadocTokenDeadlineError` (refresh not started for lack of time before the deadline), which keeps the step's code; polling keeps it as `statusError`. `PRECHECK_REJECTED` carries the `operationId` too.
- Signature policy (F5, `src/pipeline/signature-policy.ts`, CMS parsed with `src/asn1`): before signing, the `SIGNER_CERT_PATH` certificate must be inside its validity period (`CERTIFICATE_INVALID` names the expiry date); after signing, the CMS must be DER, detached, with exactly one SignerInfo whose sid is that certificate, and every embedded certificate the sid also names (issuer + serial, or SKI) byte-identical to it (`SIGNATURE_POLICY_VIOLATION`); a CMS that `src/asn1` cannot read — since F15 also a SignerInfo version other than 1 ↔ issuerAndSerialNumber / 3 ↔ SKI, or a sid with more than issuer + serial — is `INVALID_SIGNATURE` (step `policy`); a failed `/cms/verify` is `SIGNATURE_INVALID` when the math is broken and `CERTIFICATE_INVALID` when the math is valid but the certificate/chain is not (it names our certificate only when the verifier reports its thumbprint, otherwise "signer not confirmed"); a valid result must report one signer with the same SHA-1 thumbprint (case and `:`/space/`-` separators ignored). The policy does not compare the certificate's organisation (ИНН ЮЛ) or person with the seller or `Подписант` — neither does Диадок: a certificate of another organisation is posted and delivered (the chain permitting) with only МЧД warnings (`PowerOfAttorneyAttachmentStatus` `PowerOfAttorneyRequired` «…возможно, требуется МЧД», `DocflowStatus.PowerOfAttorneyGeneralStatus` Warning «Не приложена доверенность», reported in `signatureCheck.powerOfAttorney`) and the pipeline reports such a send as success/pending (D204). A production run needs the seller's own certificate or an МЧД; kept as is on purpose.
- Env validation at CLI start (D20, at parity since F13): the Диадок config (`src/diadoc/config.ts`) rejects the `.env.example` placeholder `changeme` in `DIADOC_API_URL`/`CLIENT_ID`/`CLIENT_SECRET`/`REFRESH_TOKEN`, allows `http` only for `localhost`/`127.0.0.1`/`[::1]` (`DIADOC_API_URL`, `DIADOC_TOKEN_URL`), refuses credentials (userinfo) in both without echoing them (F12) and rejects a query/fragment in `DIADOC_API_URL`. The signer config (`src/signer/config.ts`, → `SIGNER_CONFIG`) requires `https` for `CRYPTOARM_SERVER_URL`, `http` only for loopback and the compose service name `cryptoarm-server` (then `parseBaseUrl` in `src/signer/shared.ts` refuses credentials/query/fragment); refuses `SIGNER_KIND` other than `server`/`diadoc-test` (also the removed `documents`) and the placeholders `changeme`/`change-me-api-key` in `CRYPTOARM_SERVER_API_KEY`; and parses `SIGNER_CERT_PATH` (PEM → DER, non-DER lengths or a non-X.509 file refused, `.pfx`/`.p12` refused by name). The pipeline config (`src/pipeline/config.ts`, → `PIPELINE_CONFIG`) rejects `changeme` box ids and requires `DIADOC_FROM_BOX_ID` ≠ `DIADOC_TO_BOX_ID`. On the host, unquoted `.env` values are cut at `#` (`node --env-file`): quote them or use `*_FILE`.

## Secrets

КриптоАРМ API keys, КриптоАРМ Server/КриптоПро licenses, Диадок `client_secret`/`refresh_token`, PFX containers and PINs go only into untracked `.env` files or the git-ignored `secrets/` directory of the stand (`docker/cryptoarm-server/secrets`; preferred since I5; `docker/cryptoarm-documents/` of the removed Документы stand stays git-ignored in case its secrets are still on disk); commit `.env.example` with placeholders only — never real values.
